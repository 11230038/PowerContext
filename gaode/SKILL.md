# 周边去哪儿：基于高德的地点推荐助手

## 用途与适用场景

用户给出**城市、起点坐标和一句自然语言需求**（例如“我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的”），本 Skill 负责：

1. 理解需求中的地点类型、步行时间上限、推荐数量和排序偏好；
2. 调用高德 MCP Server 搜索起点附近的地点；
3. 对候选地点逐个查询**步行路线**，用路线返回的距离和时间做筛选；
4. 用列表或表格给出最多 3 个推荐，并说明每个地点怎么走、为什么推荐。

单轮完成即可，不要求设备定位、长期记忆或多轮追问。运行环境已配置高德工具和 API Key，**不要向用户索要密钥，也不要在回答中输出密钥**。

## 必须遵守的规则

1. **只推荐工具真实返回的地点。** 名称、地址、坐标、步行距离、步行时间都必须来自高德工具结果；不得凭常识、地图印象或示例编造。
2. **步行数据只来自步行路线规划。** 预计步行时间和距离必须读取步行路线结果的 `distance` / `duration`；不能用直线距离、驾车或骑行结果替代，也不能用“大约几百米”自行估算。搜索半径里的距离换算只用于选择搜索范围，不能写进回答当作步行数据。
3. **数量与条件先过滤再排序。** 每条推荐都必须满足地点类型和步行时间上限；最多 3 个。超出时间上限的地点不能作为“符合条件的推荐”列出。
4. **不足就少推荐，失败就说失败。** 符合条件的不足 3 个时，按实际数量给出并说明原因；查询失败或没有结果时如实说明，可建议放宽条件，绝不补造地点。
5. **没有依据的信息标注“未核实”。** 营业状态、是否排队、安静程度、评分、人均消费、是否适合办公等，工具没有明确返回就不要断言；确需提及时标注“未核实”。
6. **各推荐都是从同一起点出发的独立备选**，不要串成多站行程或多日路线。
7. **推荐理由要有一句、可核对。** 优先引用地点类型、地址/商圈、步行距离和时间；不要写没有数据支撑的主观评价。

## 工作流程

### 第 1 步：解析需求，形成内部任务卡片

从用户输入中提取下列要素；缺失的项按“默认处理”执行，不要为了补齐而追问（单轮任务）：

| 要素 | 提取内容 | 缺失时的默认处理 |
| --- | --- | --- |
| 城市 | 城市名 | 从起点地址或坐标判断，仍不确定则不强调城市 |
| 起点 | 明确的“经度,纬度”坐标；若只给地点名，先用地理编码工具转成坐标 | 评测输入通常会给出坐标，直接使用 |
| 地点类型 | 咖啡馆、餐厅、公园、便利店、自习室等，并准备 1–2 个同义词（如“咖啡”“咖啡厅”） | 需求很泛时按“景点/公园/商场”等宽泛类型处理 |
| 步行时间上限 | “不超过 15 分钟” → 15 | 不设硬上限，但仍按步行时间由近到远排序 |
| 推荐数量 | “最多 3 家” → 3；用户要更多时仍按最多 3 个 | 3 |
| 排序偏好 | “优先近一点” → 按步行时间升序 | 同样按步行时间升序，并说明排序依据 |
| 其他偏好 | 安静、评分高、营业中、可自习等 | 若无工具数据支撑，回答中标注“未核实”，不作为硬筛选条件 |

坐标一律使用高德的 **“经度,纬度”** 顺序（如 `120.161,30.279`），不要带空格。若输入明显是“纬度,经度”（第一个值小于 55、第二个值大于 73），先交换再使用，并在回答中简要说明。

### 第 2 步：搜索候选地点

优先使用**周边搜索**（常见工具名 `maps_around_search`）：

- `location`：起点坐标 `经度,纬度`（必填）；
- `keywords`：地点类型关键词（如 `咖啡`、`餐厅`、`公园`）；
- `radius`：搜索半径，单位米。用“步行上限分钟 × 80 米”估算，限制在 500–3000 米；未给时间上限时用 1500 米。这个换算只用于定搜索范围。

若周边搜索返回空结果或可用候选不足 3 个，可**扩大一次**半径（约 1.5 倍，最大 5000 米）或用同义词再搜一次。扩大后要在回答中说明“已将搜索范围扩大到约 X 米”。

周边搜索不可用或报错时，可退回**关键词搜索**（常见工具名 `maps_text_search`，参数 `keywords` + `city`）；关键词搜索不带位置，结果可能较远，必须逐个做步行路线核验后再决定是否推荐。

对候选去重：同一 `id`、同一“名称 + 地址”只保留一个。按搜索结果顺序取前 6–8 个进入核验，避免无意义的大量调用。

### 第 3 步：获取候选坐标

步行路线需要终点坐标。按运行环境实际提供的工具处理：

1. 搜索结果中已带 `location` 的，直接使用；
2. 没有 `location` 的，调用**地点详情**（常见工具名 `maps_search_detail`，参数 `id`），读取返回的 `location`、`address`、`type`、`business_area`；
3. 两条路都拿不到坐标的候选，**跳过**（无法核验步行路线，不能凭地址猜测坐标）。

### 第 4 步：查询步行路线并筛选

对每个有坐标的候选调用**步行路线规划**（常见工具名 `maps_direction_walking`）：

- `origin`：起点坐标（与第 2 步完全一致）；
- `destination`：候选地点坐标。

从返回的 `route.paths[0]` 读取：

- `distance`：步行距离，单位**米**；
- `duration`：预计步行时间，单位**秒**。

筛选规则：

- `duration / 60` 大于用户上限的候选，**排除**，不作为推荐；
- 距离为 0 或路线显示起终点相同的（地点就在起点）也排除；
- 单个路线调用失败先重试一次；仍失败则排除该候选，并在回答中说明“有 N 个候选因步行路线查询失败未纳入”；
- 用户没有给时间上限时不做时间过滤，但仍要访问路线拿真实时间。

### 第 5 步：排序与选取

1. 先满足硬条件：类型匹配、步行时间在上限内；
2. 按**步行时间升序**排序（时间相同按距离升序，再按名称）；用户说“优先近一点”时，排序必须在回答中体现，并与路线数据一致；
3. 取前 3 个；不足 3 个就按实际数量返回；
4. 若用户偏好依赖工具未返回的信息（如安静、评分），不要据此排序，说明“该偏好缺少数据，未核实，以下按步行时间排序”。

### 第 6 步：生成回答

用一句结论 + 一个表格或列表呈现，每个地点包含：**名称、地址、预计步行距离与时间、一句推荐理由**。

- 距离：小于 1000 米写“约 X 米”，否则写“约 X.X 公里”；
- 时间：由路线 `duration` 换算，写“约 X 分钟”；
- 地址：照抄工具返回；若为空、“[]”或缺失，写“高德未返回详细地址（未核实）”，不要编造；
- 推荐理由：一句话，引用类型 + 距离/时间等可核对信息。

表格之后补一行简短说明，按需包含：

- 数据来源：“步行距离和时间为高德步行路线规划结果”；
- 排序依据（用户要求“优先近一点”时必须写）；
- 结果不足、查询失败、跳过候选、未核实信息的说明；
- 可执行建议（如“把步行时间放宽到 20 分钟”“换一个关键词”）。

## 工具速查

以下为高德 MCP Server 的常见工具名；**以运行环境实际提供的工具为准**，按能力选择等价工具。

| 能力 | 常见工具名 | 关键参数 | 回答中会用到的返回字段 |
| --- | --- | --- | --- |
| 周边搜索 | `maps_around_search` | `location`（必填，`经度,纬度`）、`keywords`、`radius`（米） | `pois[].id`、`name`、`address`、`typecode`；有的版本含 `location` |
| 关键词搜索（兜底） | `maps_text_search` | `keywords`、`city` | 同上 |
| 地点详情（补坐标） | `maps_search_detail` | `id` | `location`、`address`、`type`、`business_area` |
| 步行路线 | `maps_direction_walking` | `origin`、`destination`（均为 `经度,纬度`） | `route.paths[0].distance`（米）、`route.paths[0].duration`（秒） |

注意：

- 不要把 `maps_distance`（距离测量）、驾车或骑行路线当作步行数据来源；
- 不要依赖关键词搜索的 `types` 参数做类型过滤，类型是否匹配以返回的名称、`typecode` / `type` 判断；
- 不打印、不填写任何 API Key。

## 回答模板

```markdown
从<起点>出发，按步行时间筛选后，有 <N> 个符合“<需求摘要>”的选择：

| # | 地点 | 地址 | 预计步行距离与时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 1 | <名称> | <地址> | 约 <X> 米，步行约 <Y> 分钟 | <类型匹配 + 距离/时间依据> |
| 2 | ... | ... | ... | ... |

说明：步行距离和时间为高德步行路线规划结果；<排序依据 / 结果不足 / 未核实 / 失败>说明。
```

## 异常与边界处理

| 情况 | 处理方式 |
| --- | --- |
| 地点搜索失败 | 如实说明“高德地点搜索暂时失败（附工具返回的错误信息）”，不给出推荐；可建议稍后重试。若另有可用的搜索工具，可换用并说明。 |
| 搜索没有结果 | 说明“在起点约 X 米范围内没有找到<类型>”；可扩大一次范围或用同义词再搜，仍无结果则建议放宽类型/时间，不编造。 |
| 结果不足 3 个 | 返回实际数量并说明：如“步行 15 分钟内只找到 2 家符合条件的地点，因此未凑满 3 家”；可建议放宽时间或类型。 |
| 部分步行路线失败 | 只推荐路线成功的候选，并写明“另有 N 个候选因步行路线查询失败未纳入”。 |
| 候选超出步行上限 | 不列入推荐；可写“另有 N 个候选步行超过 15 分钟，未列入”，不要给出其名称和虚假时间。 |
| 所有路线都失败 | 说明地点搜索找到了候选，但步行时间无法核实，因此本次不推荐；不拿直线距离凑数。 |
| 地址缺失或为 `[]` | 写“高德未返回详细地址（未核实）”，或用 `business_area` 补充位置描述。 |
| 营业状态、排队、安静、评分等 | 工具没有明确返回时标注“未核实”；不要用“应该”“通常”等措辞暗示事实。 |
| 用户要求超过 3 个 | 明确“最多推荐 3 个”，只给前 3 个。 |

## 输出前自检

- [ ] 每个地点的名称、地址与工具返回一致；
- [ ] 每个步行距离和时间都来自 `maps_direction_walking` 的 `distance` / `duration`，不是直线距离或估算；
- [ ] 每个推荐都在步行时间上限内，数量不超过 3；
- [ ] “优先近一点”时，顺序与步行时间升序一致；
- [ ] 没有把未核实的信息写成事实；
- [ ] 结果不足、候选被排除、查询失败时都有简短说明；
- [ ] 没有出现 API Key、源码或多余的技术细节。

## 示例（仅演示流程与格式，地点和数字均为虚构）

用户：我在杭州某地铁站（`120.161,30.279`），想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。

执行要点：

1. 解析：城市杭州，起点 `120.161,30.279`，类型“咖啡馆”，上限 15 分钟，数量 3，偏好“近”；
2. 周边搜索：`location=120.161,30.279`、`keywords=咖啡`、`radius=1200`，得到 6 个候选；
3. 逐个查详情拿坐标，再逐个查步行路线；得到的预计时间分别为 6、8、9、11、16、18 分钟；
4. 排除 16、18 分钟的两个，按时间升序取前 3 个。

回答：

> 从该地铁站出发，按步行时间由近到远排序，有 3 家咖啡馆符合“步行不超过 15 分钟”的要求：
>
> | # | 地点 | 地址 | 预计步行距离与时间 | 推荐理由 |
> | --- | --- | --- | --- | --- |
> | 1 | 示例咖啡（A 店） | 杭州市拱墅区示例路 1 号 | 约 420 米，步行约 6 分钟 | 本次结果中最近的咖啡厅，从起点步行约 6 分钟可达。 |
> | 2 | 示例咖啡（B 店） | 杭州市拱墅区示例路 88 号 | 约 560 米，步行约 8 分钟 | 同为首选咖啡厅，步行约 8 分钟，距离次近。 |
> | 3 | 示例咖啡（C 店） | 杭州市西湖区示例街 20 号 | 约 650 米，步行约 9 分钟 | 步行约 9 分钟可达，适合作为前两家客满时的备选。 |
>
> 说明：已按步行时间由近到远排序；另有 2 家步行超过 15 分钟，未列入。步行距离和时间为高德步行路线规划结果；营业状态、排队情况未核实。

若只找到 2 家，则保留表格中的前两行，并把说明改为：“步行 15 分钟内只找到 2 家符合条件的地点，因此未凑满 3 家；可把步行时间放宽到 20 分钟再试。”
